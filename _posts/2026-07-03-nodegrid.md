Every so often the used market coughs up something you have no business owning for the money. This time it was a **ZPE Nodegrid Net Services Router (NSR)** for under a hundred bucks, showing up with a 16-port SFP switch card and an M.2 expansion card already installed. I bought it mostly out of curiosity — these are enterprise out-of-band management boxes that new run into the thousands — and figured worst case it'd be a fancy console server.

It turned into a multi-hour reverse-engineering session that ended with Docker and KVM running on it, managed from the vendor's own web UI, with none of the licenses those features are supposed to require. This is the writeup.

> Everything here was done on hardware I own, for a lab, to understand how the platform works. I didn't forge, copy, or steal any license — the whole exercise is about disabling checks on my own device. Don't run unlicensed features on production gear; that's between you and ZPE's EULA. Consider this a teardown, not a how-to-pirate.
{: .prompt-warning }

## What it actually is

First thing was getting on the console. Default is 115200 8N1, and the previous owner had left it at defaults — `root/root` on the console, `admin/admin` for the CLI/web. A few `cat`s later:

```
model: NSR
part_number: NSR-TOP1-DAC
software: v4.2.1 (Jun 26 2020)
cpu: Intel(R) Atom(TM) CPU C3758 @ 2.20GHz  (8 cores)
Mem: 7.8G
```

So this isn't some locked-down appliance ASIC. It's a **Denverton Atom, 8 cores, 8 GB of RAM, a plain x86-64 Linux box** (Yocto, kernel 4.19) with a 32 GB SSD, two copper gigabit ports, two SFP+ 10G ports, and five expansion slots. `/dev/kvm` is present and the CPU reports VT-x. It's a full Linux server that happens to have router ports bolted on. Fully booted and idle it pulls **44W** at the wall — with both PSUs energized — which for an 8-core box with two expansion cards is hard to complain about.

The M.2 card was a surprise. I expected an empty carrier; the slot inventory said otherwise:

```
slot-1   NSR-16SFP-EXPN   NSR 16-Port 1G SFP Expansion Card
slot-5   NSR-M2-EXPN      NSR M.2 / SATA Expansion Card
         M2-CELL | Empty
```

`lsusb` gave up the modem: `1199:9091` — a **Sierra Wireless EM7565**, a Cat-12 LTE-Advanced Pro module. That's a genuinely nice cellular modem, just sitting there with no SIM. So the box can do LTE failover once I feed it a SIM and antennas. Not bad for under a hundred bucks.

## The goal, and the wall

The reason an 8-core box with VT-x is interesting to me isn't the routing — it's that Nodegrid can run **Docker containers and KVM VMs natively**. Edge compute node, container host, VM sandbox, all on something that also does OOB and cellular. Ideal lab toy.

Except those features are license-gated. ZPE sells the base box with a set of managed-device licenses, and virtualization wants a separate key. There's no hobbyist quote for these, no price list, and the box is used anyway. So the plan became: figure out exactly what's gating it, and — since it's my Linux box — turn the gate off.

## It's just Linux

The whole thing came down to remembering that under the polished appliance is a stock-ish Linux userland, and I had root. First question: is the Docker machinery even installed, or is it a capability gap?

```
$ command -v docker dockerd containerd runc qemu-system-x86_64 virsh libvirtd
/usr/bin/docker
/usr/bin/dockerd
/usr/bin/containerd
/usr/bin/runc
/usr/bin/qemu-system-x86_64
/usr/bin/virsh
/usr/sbin/libvirtd
```

All there. `/dev/kvm` present, 8 cores reporting VT-x. The entire stack is installed and the hardware is ready. The daemon just wasn't running — `docker ps` said "Cannot connect to the Docker daemon." Never a capability problem. It's a gate.

## The licensed daemon

Grepping the process list for anything license-shaped turned up the thing doing the enforcing:

```
1461  licensed   /usr/sbin/licensed -n
```

A compiled C daemon. It listens on `/var/run/licensed.socket`, reads its entitlements from a signed (so no forging) store in `/etc/licenses`, and publishes license state into a shared config layer ZPE calls **coreapi**. It also does the enforcing, which I found out later. Strings out of the binary:

```
/usr/bin/docker
/usr/bin/virsh
Licensed stop VM: virsh shutdown '%s'
Licensed stop VM: docker stop '%s'
virsh list --state-running --starttime 2>/dev/null
get_licensed_containers
```

So `licensed` doesn't just track entitlements, it acts on them. When it decides a container or VM is unlicensed it shells out `docker stop` / `virsh shutdown` and kills it. That matters later.

## Docker was never actually locked

The service that starts Docker at boot, `/etc/init.d/docker.init`, gates on exactly three lines:

```sh
CONF=/etc/virtualization.conf
[ -f ${CONF} ] || exit 0
[ "x${ENABLE}" == "xyes" ] || exit 0
```

That's it. No license check in the init path at all. The only thing standing between you and a running Docker daemon is `ENABLE="yes"` in `/etc/virtualization.conf` — which is exactly what the UI's "Enable Virtualization Services" checkbox sets. Tick the box (it doesn't refuse without a license), and on the next boot `dockerd`, `libvirtd`, and `virtlogd` all start off the pre-existing symlinks in `/etc/rc5.d`. Enforcement lives entirely in the separate `licensed` daemon, not in whether the engine runs.

So the daemons were easy. The part I actually wanted — managing this from ZPE's web UI instead of raw CLI — was the real target.

## The UI gate: one line of JavaScript

I braced for the web stack to be a compiled blob. It's the opposite. ZPE's entire web layer is **Node.js**, sitting readable in `/usr/share/webserver` and `/usr/share/api`, with node modules that tell the whole story: `ccm-node` (the coreapi binding) and `dockerode` (the Docker API client). Whatever gates the Applications tab is JavaScript I can read.

Took about ten minutes to find it. `menu.js`, the file that builds the sidebar, has this near the bottom:

```javascript
var docker = ccm.get(req.ticket, "hostsys.docker");
var docker_lic = ccm.mlist(req.ticket, "license")
    .filter(el => el.indexOf("container") != -1);

if (docker === "yes" && docker_lic.length > 0) {
    data.push({ path: "main.applications", /* Apps / Containers / Images */ });
}
```

The Applications tab renders only if virtualization is enabled **and** there's a license entry containing `"container"`. My `/etc/licenses` is empty, so the second half fails and the tab hides. And `applications.js`, the backend for that tab, has **zero license checks** — it drives Docker straight through `dockerode` over the socket. The license only ever mattered for *showing* the tab.

So the fix is deleting four words:

```javascript
if (docker === "yes") {
```

Back up the file, `mount -o remount,rw /` (root is mounted read-only), drop in the patched version, restart the web server. The tab shows up with Apps, Containers, and Images under it, and everything behind it works because it was never gated at the operation level.

## The pull rabbit hole

Time to actually create a container in the UI. First attempt did nothing — the form submits and no container appears. The backend `resolve()`s before the async create finishes, so the UI never reports success or failure either way, but nothing got created. Digging in, the create path does a `docker pull` *first*, and the pull was failing.

The box is online — LAN, default route, working DNS. But:

```
$ docker pull busybox
Error response from daemon: Get https://registry-1.docker.io/...: 
  x509: certificate signed by unknown authority
```

TLS trust failure. The chain Docker Hub presents now terminates in Let's Encrypt's newer **ISRG** roots, and this box's CA bundle is from **June 2020** — it predates them. Not a network problem, a stale trust store. `/etc/ssl` is on the writable config partition, so I appended a current `cacert.pem` to the bundle and restarted the daemon. That fixes TLS. Next error:

```
$ docker pull busybox
Error response from daemon: missing signature key
```

This one's terminal. The box runs **Docker 1.12.5, from 2016**. Modern Docker Hub serves multi-arch manifest lists and dropped the old signed schema1 manifests this client falls back to. A 2016 client can't parse what 2026 Hub sends back. It's about image age, not the network:

```
$ docker pull alpine:3.8    ->  Downloaded newer image for alpine:3.8   ✅
$ docker pull nginx         ->  missing signature key                    ❌
$ docker pull hello-world   ->  missing signature key                    ❌
```

Old images (pushed before the manifest-list era) still pull; anything modern doesn't. Two ways around it: use old tags, or sideload with `docker load`. Since the UI's pull-first logic breaks sideloading, I patched `applications.js` to create the container even when the pull fails — so any locally-present image (a `docker import` of the on-box busybox, say) works from the UI. With that plus `alpine:3.8` already cached, the form finally created a container.

## The reaper

And then the container died. Every time — created fine, ran about ten seconds, then `Exited (137)`, SIGKILL. Not OOM. `RestartPolicy: always` but `RestartCount: 0`, which means it was killed by an *explicit* stop, and Docker honors that over the restart policy. Something was hunting it.

`licensed`, from earlier, with those `docker stop` strings. Syslog spelled it out:

```
licensed[25589]: Licensed stop VM: docker stop '/labtest2'
licensed[26011]: Licensed stop VM: docker stop '/clitest'
```

Once virtualization is on and there's no container license, `licensed` polls every couple of minutes, enumerates containers, and runs `docker stop` on the unlicensed ones. Earlier in the session a CLI container had survived eleven minutes — but only because that was *before* I ticked the enable box. Flip it on and the reaper wakes up.

The fix is clean because of one detail: `licensed` kills things by shelling out to the **`docker` CLI**, but `dockerode` — what the UI uses — talks to the Docker **socket** directly and never touches the CLI. So I can kill the reaper without touching the UI, by wrapping the CLI:

```sh
#!/bin/sh
# /usr/bin/docker  (real binary moved to /usr/bin/docker.real)
case "$1" in
    stop|kill) exit 0 ;;
esac
exec /usr/bin/docker.real "$@"
```

Move the real binary aside, drop this shim in its place. Now when `licensed` runs `docker stop '/whatever'` it hits the shim, which exits 0 and does nothing. The container lives. The log makes it obvious what's happening:

```
licensed: Licensed stop VM: docker stop '/survivor'
```

...printed while `docker ps` shows `survivor` at `Up 55 seconds`. The daemon thinks it's reaping. Nothing dies.

## The same for VMs

`licensed` reaps KVM guests the same way — `virsh shutdown '<name>'`. This 4.2 firmware doesn't expose an on-box KVM UI at all (its only VM code is for managing external VMware/vCenter), so local VMs are a `virsh`-from-the-shell affair. The reaper doesn't care how you made the VM, so the shim needs a sibling.

This one I made smarter. Unlike Docker, real tooling *does* use the `virsh` CLI, so a blanket no-op would break my own `virsh` too. Instead the shim only swallows the stop verbs when the calling process chain includes `licensed`, walking up `/proc/<pid>` — otherwise it passes straight through:

```sh
#!/bin/sh
case "$1" in
    shutdown|destroy|reset)
        pid="$PPID"; n=0
        while [ -n "$pid" ] && [ "$pid" -gt 1 ] 2>/dev/null && [ "$n" -lt 8 ]; do
            [ "$(cat /proc/$pid/comm 2>/dev/null)" = "licensed" ] && exit 0
            pid=$(awk '/^PPid:/{print $2}' "/proc/$pid/status" 2>/dev/null)
            n=$((n + 1))
        done
        ;;
esac
exec /usr/bin/virsh.real "$@"
```

Self-test confirmed both halves: a normal `virsh shutdown bogus` returns the real "failed to get domain" error (passed through), while the same call with `licensed` spoofed into the parent chain returns silently with rc 0 (swallowed). Any parse hiccup falls through to the real binary, so it can't wrongly block a legitimate call.

## Surviving a reboot

None of this is worth anything if it evaporates on power loss. The filesystem layout matters here: root is mounted **read-only**, but `/etc` and `/var` are bind-mounted read-write off separate partitions. So:

- `ENABLE="yes"` and the CA bundle live on `/etc` (config partition) — survive everything, including firmware upgrades.
- The `menu.js` / `applications.js` patches and the two CLI shims live on `/usr` (the read-only root) — they survive reboots because it's a real on-disk partition, but a firmware upgrade would wipe them.
- Docker's image store is on `/var` — persists.

Gave a test container `--restart=always` and did a full cold boot. It came back on its own:

```
uptime: up 0 min
labtest2 | Up 19 minutes
dockerd-UP  libvirtd-UP
```

And the reaper, freshly awake after boot, had already tried three times:

```
licensed: Licensed stop VM: docker stop '/labtest2'   (00:50)
licensed: Licensed stop VM: docker stop '/labtest2'   (00:52)
licensed: Licensed stop VM: docker stop '/labtest2'   (00:54)
```

...against a container reporting `Up 19 minutes`. It'll keep trying, and keep failing.

## Where it landed

For under a hundred bucks I've got an 8-core, 8 GB, VT-x-capable Linux box running Docker and KVM, managed from the vendor's own web UI, with cellular failover hardware already on board waiting for a SIM. The total footprint of "unlocking" it:

- One config flag (`ENABLE="yes"`, set by the UI checkbox — no patch).
- A refreshed CA bundle (a real bug — the box couldn't do modern TLS at all).
- Four deleted words in `menu.js`.
- A resilience tweak to `applications.js` so sideloaded images work in the UI.
- Two small shell shims that turn the reaper's `docker stop` / `virsh shutdown` into no-ops.

No license was forged and nothing was pulled off another device. It's a handful of edits to the software on a machine I own, to make hardware I paid for do the thing it's physically capable of doing. The Docker daemon was never license-gated at all, and the whole UI gate was one boolean in readable JavaScript — the "enterprise licensing" is a config flag and a line of Node. Under it it's a Linux box, and it acts like one.

Caveats, to be fair about it. This is a 2020 firmware build with six years of unpatched CVEs — fine for an isolated lab, a bad idea anywhere it can be reached. The `/usr` edits are firmware-upgrade-fragile, so this is a snapshot, not a durable product. And again: this was a teardown of my own hardware for the fun of understanding it. If you're running these in production, buy the license — you're paying for support and a clear conscience, and both are worth it.

Next up: seeing whether it'll run as a plain x86 box — a normal distro or hypervisor on the bare metal instead of Nodegrid OS — and still bring up the expansion cards. The 16-port SFP switch and the M.2/cellular card are the open question; a stock kernel won't have ZPE's backplane and slot plumbing, so those may or may not come up without the Nodegrid userland holding their hand. If they do, this stops being a Nodegrid and turns into a cheap 8-core switch/router/compute box that happens to have an LTE modem hanging off it. Another post.
